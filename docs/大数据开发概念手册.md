## 一、大数据工程师是干什么的

### 1.1 一句话定义

**把分散在各处的数据，稳定、准确、准时地变成能用的数据（报表、指标、接口、模型输入）。**

不是"研究数据"，也不是"训练 AI"，本质是**数据管道和数据处理系统的建设者**。

### 1.2 数据的完整旅程

```
数据产生                     数据汇聚              数据加工              数据服务
App/车机/服务端/数据库  →  采集、同步到湖仓  →  清洗、建模、计算  →  报表/接口/画像/模型
     ↑                          ↑                   ↑                  ↑
   业务开发                 数据采集/同步        大数据开发(主战场)     数据分析/算法
```

大数据工程师主要站在**中间两段**：把数据搬进来、把数据算出来。

### 1.3 典型的一天

| 占比 | 工作内容 |
|---|---|
| 30% | **写 SQL / 写任务**：清洗明细、建汇总表、算指标 |
| 25% | **排查问题**：任务失败、数据延迟、指标对不上、数据倾斜 |
| 15% | **需求对接**：和产品/运营/分析师确认"这个指标到底怎么算" |
| 10% | **优化**：跑得太慢、资源太贵、链路不稳定 |
| 10% | **上线与运维**：调度配置、监控告警、补数 |
| 10% | **评审与文档**：模型设计评审、口径文档 |

**真相**：不是天天写高大上的分布式代码，**大部分时间在写 SQL 和修数据**。

### 1.4 岗位细分

| 细分 | 干什么 | 核心技术 |
|---|---|---|
| **数仓开发 / 离线开发** | 分层建模、ETL、指标开发，T+1 出数 | Hive SQL、Spark SQL、调度 |
| **实时开发** | 秒级/分钟级指标、实时链路、风控 | Flink、Kafka、OLAP |
| **数据平台 / 中间件** | 集群搭建、组件运维、平台工具开发 | Hadoop 生态、K8s、Java |
| **数据集成 / 采集** | 异构数据源同步、CDC、埋点采集 | DataX、Flume、Canal、SDK |
| **AI 数据工程**（新） | 为模型准备训练/检索数据、向量化管道 | Spark、向量库、RAG 数据管道 |

多数公司的"大数据工程师"= 数仓开发 + 离线开发，实时是加分项。

### 1.5 和容易混淆的岗位的区别

| 岗位 | 核心问题 | 产出 |
|---|---|---|
| **大数据工程师** | 数据怎么**存、算、稳** | 数据表、数据任务、数据链路 |
| 数据分析师 | 数据**说明什么** | 分析报告、结论、建议 |
| 算法工程师 | 数据能**预测什么** | 模型、策略 |
| 后端工程师 | 业务**功能**怎么实现 | 接口、服务 |
| DBA / 运维 | 数据库/集群怎么**不挂** | 稳定性 |

一句话区分：**大数据工程师负责"把数据准备好"，分析师负责"解释数据"，算法负责"用数据做预测"。**

### 1.6 常见误解

| 误解 | 实际 |
|---|---|
| "天天写分布式框架源码" | 95% 的时间在用现成组件，写 SQL 和任务 |
| "数据量大就很厉害" | 真正的难点是**数据准、链路稳、成本低**，不是量大 |
| "不用懂业务" | 不懂业务写不出正确指标，口径错一次就是线上事故 |
| "是 AI 岗位" | 不是。但 AI 越普及，"可信数据"越值钱 |
| "不用写代码" | 要写，只是语言从 Java/Kotlin 换成了 SQL + Scala/Python |

### 1.7 决定水平高低的三件事

1. **数据准确性**：指标口径统一、可追溯、能自证（最核心）
2. **链路稳定性**：延迟可控、失败可恢复、有监控有告警
3. **成本与效率**：同样的结果，算得更快、花得更少

写 SQL 谁都会，AI 也会。**能对"数据对不对、链路稳不稳、钱花得值不值"负责的人，才稀缺。**

## 二、核心交付物：数据表、数据任务、数据链路

用一个具体需求串起来：**"每天出一张 App 日活指标表"**。

### 2.1 数据表：数据的容器

就是数仓里的一张表，和 MySQL 表概念一样，只是存在 Hive/Doris 里，按天分区、数据量大。

```sql
-- ADS 层：每日活跃用户指标表
CREATE TABLE ads.ads_app_dau_d (
    dt            STRING  COMMENT '统计日期',
    app_version   STRING  COMMENT 'App 版本',
    channel       STRING  COMMENT '渠道',
    dau           BIGINT  COMMENT '日活用户数',
    new_user_cnt  BIGINT  COMMENT '新增用户数'
)
PARTITIONED BY (pt STRING)   -- 按天分区，如 pt='20261127'
COMMENT 'App 日活指标表';
```

一张合格的表要交代清楚：

| 要素 | 说明 |
|---|---|
| Schema | 字段名、类型、注释（**注释必须写**，否则没人知道 `col_3` 是什么） |
| 分区 | 按天/小时切分，是查询剪枝和补数的基础 |
| 分层归属 | ODS / DWD / DWS / ADS，决定它给谁用 |
| 生命周期 | 保留 7 天 / 1 年 / 永久 |
| 负责人 | 出问题找谁 |

**产出表 = 定义好结构 + 写清口径 + 能稳定产出数据**，不是建个空表就完事。

### 2.2 数据任务：往表里算数据的程序

任务就是一段**定时执行的代码**，输入若干张表，输出一张表。

```sql
-- 任务名：ads_app_dau_d_daily
-- 调度：每天 03:00
-- 上游依赖：dws_app_user_active_1d（当天分区跑成功）
INSERT OVERWRITE TABLE ads.ads_app_dau_d PARTITION(pt='${bizdate}')
SELECT
    '${bizdate}' AS dt,
    app_version,
    channel,
    COUNT(DISTINCT user_id)                             AS dau,
    COUNT(DISTINCT CASE WHEN is_new=1 THEN user_id END) AS new_user_cnt
FROM dws.dws_app_user_active_1d
WHERE pt = '${bizdate}'
GROUP BY app_version, channel;
```

一个任务除了代码，还包含：

| 要素 | 说明 |
|---|---|
| 输入 / 输出 | 读哪些表、写哪张表哪些分区 |
| 调度周期 | 每天 / 每小时 / 每 5 分钟 |
| 依赖关系 | 上游任务成功才跑 |
| 失败策略 | 重试次数、超时时间、告警给谁 |
| 资源 | 用多少 CPU/内存（Spark 任务） |
| 重跑能力 | 指定日期能单独补跑（补数） |

**任务 = 代码 + 调度 + 依赖 + 监控**，只写 SQL 不配调度，等于没交付。

### 2.3 数据链路：任务连起来的流水线

单个任务没意义，数据要一层层加工，形成一条从源头到应用的链：

```
[App 埋点日志]
      │  采集任务(Filebeat/Flume → HDFS)
      ▼
ods.ods_app_event_log_d          ← ODS：原始日志，一行一个事件
      │  清洗任务(Spark，去脏数据/解析 JSON/会话切分)
      ▼
dwd.dwd_app_event_detail_d       ← DWD：干净明细，一行一个用户行为
      │  汇总任务(Spark，按用户/天聚合)
      ▼
dws.dws_app_user_active_1d       ← DWS：用户粒度日汇总
      │  指标任务(Spark SQL)
      ▼
ads.ads_app_dau_d                ← ADS：直接给报表用的指标
      │
      ▼
BI 看板 / 数据接口 / 用户画像
```

这条 DAG（有向无环图）就是**链路**。它要保证：

| 链路级要求 | 说明 |
|---|---|
| 依赖正确 | 上游没跑完，下游不能跑 |
| SLA | 约定每天 7:00 前必须产出，晚了要告警 |
| 可追溯 | 数据错了，能顺着血缘找到是哪一环的问题 |
| 可补数 | 某天数据错了，能一键重跑整条链 |
| 可监控 | 每环的耗时、数据量、失败率都有看板 |

### 2.4 三者关系

```
数据表   = 节点（存什么）
数据任务 = 边上的加工动作（怎么算）
数据链路 = 整张图（整体怎么流转、能不能按时按质产出）
```

- 表是**静态产物**，任务才是**动态劳动**
- 一条典型链路包含 **3~10 张表 + 3~10 个任务**
- 面试问"你负责什么"，答"我负责 X 域 20 张表、15 个任务、3 条链路"，比"我写 SQL"具体得多

### 2.5 Android 类比

| 大数据概念 | Android 里的对应物 |
|---|---|
| 数据表 | 本地数据库表 / 接口返回的 Bean 结构 |
| 数据任务 | 定时任务 / 后台 Job / 一个接口的后端实现 |
| 数据链路 | 一次请求的完整调用链：UI → ViewModel → Repository → API → DB |
| 链路监控告警 | 线上崩溃监控 + APM 链路追踪 |
| 补数 | 用户反馈某天数据不对，重新跑一次同步 |

### 2.6 真实交付节奏

一个典型需求（如"新增渠道维度的日活"）：

1. **对齐口径**：和产品/分析师确认"日活"怎么算（去重？含游客？）
2. **设计表**：确定放 ADS 层，加 `channel` 字段，改表结构
3. **改任务**：修改 SQL，加 join 渠道维表
4. **配调度**：确认依赖没变、跑一次补历史数据
5. **验证**：和旧数据对比、和业务方对数
6. **上线 + 监控**：观察 2~3 天数据量是否异常

## 三、存储与查询系统：Hive 与 Doris

两者都是**存数据、用 SQL 查数据**的系统，但定位完全不同：
**Hive 是离线加工的"中央厨房"，Doris 是在线查询的"前台门店"。**

### 3.1 Hive：离线数仓的加工厂

**是什么**：跑在 Hadoop 上的 SQL 数仓工具。你写 SQL，它翻译成 MapReduce / Spark / Tez 任务去跑。

| 维度 | 情况 |
|---|---|
| 数据存在哪 | HDFS（分布式文件系统），本质是**一堆文件** |
| 适合什么 | 海量数据的**批量加工**（TB~PB 级、T+1） |
| 速度 | 慢，一个查询几分钟到几十分钟很正常 |
| 能力 | 只支持"整表/整分区写入覆盖"，**不支持单行更新、不支持高并发点查** |
| SQL | Hive SQL，和 MySQL 很像，但有差异（分区必须指定等） |
| 成本 | 便宜，存 HDFS + 跑批任务 |

**关键认知**：Hive 不是数据库，是"SQL 外壳 + 分布式文件"。它没有索引、没有事务、没有行级更新，**只适合算，不适合查**。

### 3.2 Doris：面向查询的加速层

**是什么**：国产 MPP 架构的**分析型数据库（OLAP）**，列式存储，专为"快速查询大量数据"设计。

| 维度 | 情况 |
|---|---|
| 数据存在哪 | 自己的存储引擎（列存），不是文件堆 |
| 适合什么 | **报表、看板、实时大屏、高并发聚合查询** |
| 速度 | 快，毫秒到秒级 |
| 能力 | 支持 `UPDATE/DELETE`、主键模型、物化视图、高并发（几千 QPS） |
| SQL | 标准 SQL，兼容 MySQL 协议 |
| 成本 | 比 Hive 贵，存储和内存要求高 |

**它解决的是 Hive 解决不了的问题**：业务方打开看板，等 30 分钟出不来数——那就把结果同步到 Doris，查询变成秒级。

### 3.3 对比

| 对比项 | Hive | Doris |
|---|---|---|
| 定位 | 离线数仓加工引擎 | 在线分析数据库 |
| 架构 | 主从（HDFS + 计算框架） | MPP 大规模并行 |
| 存储 | HDFS 文件 | 列式存储引擎 |
| 查询延迟 | 分钟~小时 | 毫秒~秒 |
| 并发 | 低 | 高（上千 QPS） |
| 更新数据 | 只能覆盖分区 | 支持 UPDATE/DELETE |
| 类比 | 中央厨房批量做菜 | 门店现做现卖 |
| 常见同类 | Spark SQL、Presto/Trino | ClickHouse、StarRocks |

### 3.4 它们如何配合

```
原始日志/业务库
     │
     ▼
┌─────────────── Hive（离线数仓）───────────────┐
│  ODS 原始层 → DWD 明细层 → DWS 汇总层          │
│  每天凌晨跑批，数据量大、延迟高、成本低          │
└───────────────────────┬───────────────────────┘
                        │ 每日同步结果表
                        ▼
              Doris（查询加速层）
                        │
                        ▼
            BI 看板 / 数据大屏 / 数据接口
            （秒级响应、高并发）
```

- **Hive 负责"算得出来"**——数据量大、可以慢
- **Doris 负责"查得快"**——数据量适中、必须快

JD 里写"Hive + Doris"，不是二选一，而是要求你会搭这条**离线算 + 在线查**的完整链路。

## 四、数仓分层：ODS / DWD / DWS / ADS

一句话：**同一份数据，在数仓里会被加工四遍，每一遍放在不同层，服务不同的人。**

以"用户点了 App 里的『立即购车』按钮"为例。

### 4.1 同一份数据在四层的样子

**ODS 层（原始层）**：原封不动存下来

| pt | log_json |
|---|---|
| 20261127 | `{"uid":"u1","ev":"click_buy","ts":1732...}` |

- 一行就是一条**原始日志**，字段没解析、可能脏、可能重复
- 和源系统**一模一样**，只做落地，不做加工
- 作用：**留底**。数据算错了，永远能回到源头重来

**DWD 层（明细层）**：洗干净，变成规范的一行一事件

| event_id | dt | user_id | event_name | page | app_version | channel | event_time |
|---|---|---|---|---|---|---|---|
| e001 | 2026-11-27 | u1 | click_buy | detail_page | 5.2.0 | appstore | 10:01:23 |

- JSON 解析开、脏数据过滤掉、字段统一命名、补上维度信息
- 粒度：**一行一个用户行为**
- 作用：**全公司唯一的"干净明细事实"**，所有分析都从这里出发

**DWS 层（汇总层）**：按主题做轻度聚合

| dt | user_id | app_version | channel | click_buy_cnt | session_cnt | is_new_user |
|---|---|---|---|---|---|---|
| 2026-11-27 | u1 | 5.2.0 | appstore | 3 | 2 | 0 |

- 粒度变成：**一行 = 一个用户一天**
- 把明细里散落的行聚合成"用户维度的日汇总"
- 作用：**避免每次分析都从海量明细重算**

**ADS 层（应用层）**：直接给报表用的指标

| dt | channel | dau | click_buy_uv | conversion_rate |
|---|---|---|---|---|
| 2026-11-27 | appstore | 125000 | 3200 | 2.56% |

- 粒度：**一行 = 一个统计口径的结果**
- 字段就是报表上的那几列，BI 直接读、接口直接返回
- 作用：**口径统一的地方**，所有人看到的"日活"必须是同一张表

### 4.2 四层职责对照

| 层 | 全称 | 存什么 | 加工动作 | 给谁用 | 数据量 | 保留 |
|---|---|---|---|---|---|---|
| **ODS** | Operational Data Store | 原始数据 | 几乎不加工，只落地 | 数据开发排查 | 最大 | 短（7~30 天） |
| **DWD** | Data Warehouse Detail | 干净明细 | 清洗、解析、规范化、关联维度 | 数据开发 | 大 | 长（1 年+） |
| **DWS** | Data Warehouse Summary | 主题汇总 | 按维度聚合 | 数据开发 / 分析师 | 中 | 长 |
| **ADS** | Application Data Service | 指标结果 | 按业务口径出指标 | BI / 业务方 / 接口 | 小 | 长 |

还有一个常出现的 **DIM 层**：公共维度表（用户维、商品维、渠道维、日期维），被各层反复 join。

### 4.3 为什么要分层

| 价值 | 说明 | 反面案例 |
|---|---|---|
| **复用** | DWD 洗一次，10 个业务方都能用 | 每个需求都从原始日志重解析，重复劳动 10 倍 |
| **解耦** | App 埋点字段改了，只改 ODS→DWD，上面不动 | 源头改一个字段，50 个报表全崩 |
| **好排查** | 数据不对，逐层对数，一层层定位 | 一个数错了，不知道错在哪一步 |
| **省成本** | 汇总层预聚合，避免每次扫全量明细 | 每次查日活都扫 10 亿行日志 |

**核心逻辑：越往上越"少而精"，越往下越"全而糙"。**

### 4.4 三个容易踩的坑

1. **分层不是越多越好**：小公司常见 `ODS → DWD → ADS` 三层就够了，硬凑四层是形式主义
2. **粒度必须想清楚**：DWS 到底是"用户-天"还是"渠道-天"？粒度定错，上面全要重做
3. **ADS 不能放明细**：ADS 是给业务看的指标表，一旦有人往里塞明细，口径必乱

### 4.5 命名规范

| 前缀 | 示例 | 含义 |
|---|---|---|
| `ods_` | `ods_app_event_log_d` | 原始日志，日增量 |
| `dwd_` | `dwd_app_event_detail_d` | 明细，日分区 |
| `dws_` | `dws_app_user_active_1d` | 用户粒度，1 天汇总 |
| `ads_` | `ads_app_dau_d` | 日活指标 |
| `dim_` | `dim_channel` | 渠道维度表 |

后缀约定：`_d` 天、`_h` 小时、`_i` 增量、`_df` 全量。

## 五、技术栈全景：Hadoop、MPP、列式存储与各引擎

### 5.1 全景图

```
【第1层 地基】Hadoop = HDFS(存) + YARN(调度) + MapReduce(算)
                        │
【第2层 数仓】   离线数仓（方法论）→ 用 Hive / Spark SQL 等"数仓工具"实现
                        │
【第3层 查询】   Presto/Trino（查询网关）、ClickHouse / StarRocks（OLAP 数据库）
                              都建立在两个基础概念上：MPP 架构 + 列式存储
```

### 5.2 Hadoop

**不是一个软件，是一整套分布式基础框架**，解决一个问题：**一台机器存不下、算不完的数据，怎么用一堆便宜机器搞定。**

| 组件 | 作用 | 类比 |
|---|---|---|
| **HDFS** | 分布式存储 | 把数据分散存到很多块硬盘上 |
| **YARN** | 资源调度 | 决定哪个任务用哪台机器的 CPU/内存 |
| **MapReduce** | 分布式计算 | 把一个大计算拆成很多小计算并行跑 |

Hadoop 相当于"大数据领域的操作系统"——后面的 Hive、Spark 都跑在它上面（或借鉴它的思想）。

### 5.3 HDFS

分布式文件系统。核心机制两条：

1. **切块**：一个大文件切成固定大小的块（默认 128MB），分散存到不同机器
2. **多副本**：每块默认存 3 份，坏一台机器数据也不丢

**注意**：HDFS 是"文件"，不是"数据库"。它没有索引、不支持改一行数据、查询要全表扫。**能存，但不擅长查。**

### 5.4 离线数仓与数仓工具

**离线数仓不是软件，是一种工作模式**：

- 数据按天（或小时）**批量加工**
- 今天的数据，明天凌晨算完，早上出报表（**T+1**）
- 数据量巨大（TB~PB），**允许慢**，但要求准和稳

**数仓工具**指**能用 SQL 操作海量数据的软件**：

| 工具 | 说明 |
|---|---|
| **Hive** | 最早、最经典的数仓工具，SQL 转 MapReduce，慢但稳定 |
| **Spark SQL** | 用 Spark 引擎跑 SQL，比 Hive 快一个数量级，现在主流 |
| **Impala** | 更早的交互式查询引擎，已边缘化 |

一句话：**数仓工具 = 给 HDFS 上的一堆文件，套一个"能写 SQL"的外壳。**

### 5.5 主从架构（Master-Slave）

**一个主节点管全局，多个从节点干活。**

| 系统 | 主节点 | 从节点 |
|---|---|---|
| HDFS | NameNode（管元数据） | DataNode（存数据） |
| YARN | ResourceManager（管资源） | NodeManager（跑任务） |
| MySQL | Master（写） | Slave（读） |

- 优点：结构简单、好管理
- 缺点：**主节点是瓶颈和单点**，生产上要做 HA（主备切换）

### 5.6 MPP（Massively Parallel Processing）

**没有主从之分，所有节点地位平等，一起干活。**

查询来了 → 拆成很多片段 → **每个节点同时算自己那份** → 最后汇总。

- 主从架构 = 1 个包工头指挥 100 个工人，**包工头是瓶颈**
- MPP = 100 个人各自领一堆钱同时数，**数完汇总**

MPP 的关键是 **Shared-Nothing（无共享）**：每个节点有自己的 CPU、内存、磁盘，互不干扰，所以扩展性好、并行度高。Doris、StarRocks、ClickHouse、Presto 都是 MPP 架构。

### 5.7 列式存储

**按列存，而不是按行存。**

```
行存（MySQL/Hive 常见）        列存（OLAP 数据库）
┌────┬──────┬─────┬──────┐    user_id:  [u1, u2, u3, u4...]
│ id │ name │ age │ city │    name:     [张三, 李四, 王五...]
├────┼──────┼─────┼──────┤    age:      [25, 30, 28, 35...]
│ 1  │ 张三 │ 25  │ 北京 │    city:     [北京, 上海, 北京...]
│ 2  │ 李四 │ 30  │ 上海 │
└────┴──────┴─────┴──────┘
```

| | 行存 | 列存 |
|---|---|---|
| 存法 | 一行连续存 | 一列连续存 |
| 适合 | 按 id 查整行（OLTP） | 按列聚合统计（OLAP） |
| 聚合查询 | 要读所有列，浪费 IO | 只读需要的列，快 10~100 倍 |
| 压缩率 | 低（一行类型混杂） | 高（同列类型相同，重复度高） |
| 更新单行 | 方便 | 不方便 |

**为什么列存快？** 算"平均年龄"只需读 age 一列，行存要把 name、city 全读进来再丢掉。数据量越大差距越明显。

### 5.8 列式存储引擎

**具体实现列存的软件层**，包含：列存格式 + 压缩算法 + 索引（min/max、布隆过滤器）+ 向量化执行。

- 产品级：Doris、StarRocks、ClickHouse 的存储引擎
- 文件格式：**Parquet、ORC**（Hive/Spark 常用的列式文件格式）

一句话：**列式存储是"怎么摆"，列式存储引擎是"摆好之后还配了压缩、索引、批量计算的一套完整实现"。**

### 5.9 四个引擎/产品

**Spark SQL**

- 是什么：Spark 的结构化查询模块，用 SQL / DataFrame 写，底层是 Spark 内存计算引擎
- 特点：快（比 Hive 的 MapReduce 快 10 倍+）、支持复杂 ETL、能读写 Hive/Parquet/各种源
- 定位：**离线计算的主力发动机**，很多公司直接用它替代 Hive 做数仓
- 类比：Hive 是"老式柴油卡车"，Spark SQL 是"新款电卡"，拉的货一样，跑得快得多

**Presto / Trino**

- 是什么：分布式 **SQL 查询引擎**，**自己不存数据**
- 特点：联邦查询——一条 SQL 同时查 Hive、MySQL、Kafka、MongoDB；交互式查询快（秒级~分钟）
- 定位：**"万能查询网关"**，适合分析师做 ad-hoc 探索
- 关系：Trino 是 Presto 原团队分叉出来的，现在更活跃
- 类比：不生产数据，只是数据的搬运工和翻译官

**ClickHouse**

- 是什么：俄罗斯 Yandex 开源的**列式 OLAP 数据库**
- 特点：单表聚合**极快**（亿级数据秒出）、压缩率极高、写入快
- 短板：**多表 Join 弱**、高并发一般、不支持复杂更新
- 定位：日志分析、单表大宽表统计、实时大屏

**StarRocks**

- 是什么：国产 **MPP 列式 OLAP 数据库**，与 Apache Doris 同源
- 特点：**Join 能力强**、高并发（几千 QPS）、兼容 MySQL 协议、支持物化视图、能直接查 Hive/数据湖
- 定位：**报表 + 高并发查询 + 湖仓分析**，国内互联网/车企用得很凶

### 5.10 五个工具横向对比

| | Hive | Spark SQL | Presto/Trino | ClickHouse | StarRocks/Doris |
|---|---|---|---|---|---|
| 存数据吗 | 存（HDFS） | 不存（算完写回） | **不存** | 存 | 存 |
| 架构 | 主从 | 主从 | MPP | MPP | MPP |
| 存储方式 | 行存/列式文件 | 列式文件 | 不涉及 | 列存 | 列存 |
| 延迟 | 分钟~小时 | 分钟 | 秒~分钟 | **毫秒~秒** | **毫秒~秒** |
| 多表 Join | 一般 | 强 | 强 | 弱 | 强 |
| 高并发 | 低 | 低 | 中 | 中 | **高** |
| 典型用途 | 离线数仓 | 离线 ETL | 即席查询 | 日志/大屏 | 报表/湖仓 |

### 5.11 一条链路串起来

```
App/车机日志
   │
   ▼
HDFS 存原始文件（Hadoop 地基）
   │
   ▼
Spark SQL 每天跑批：清洗 → 分层建模 → 产出指标表（离线数仓）
   │
   ├── 分析师临时查数 → Presto/Trino 直接查 Hive（不落库）
   │
   └── 指标结果同步 → StarRocks / ClickHouse（MPP + 列存）
                          │
                          ▼
                    BI 看板 / 大屏，秒级响应
```
