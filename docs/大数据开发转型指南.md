# Android 开发转大数据开发工程师 · 学习计划与术语手册

> 适用对象：有 2 年以上 Android 开发经验、具备 Java/Kotlin 基础，希望转型大数据开发 / 数据仓库开发的工程师。
> 建议投入：每周 15~20 小时（工作日每天 2 小时 + 周末各 4~5 小时），总周期约 18 周（4~5 个月）。
> 核心策略：**项目驱动 + 先跑通再懂原理 + 用 Java 功底换赛道**。
> 配套读物：[大数据开发概念手册](大数据开发概念手册.md)（岗位职责、数据表/任务/链路、Hive/Doris、数仓分层、技术栈全景）

## 一、转型定位

### 1.1 大数据岗位方向

| 方向 | 主要工作 | 技术栈 | 转岗难度 | 建议 |
|---|---|---|---|---|
| 数据仓库开发（离线） | 数仓分层建模、ETL 开发、指标开发 | Hive SQL、Spark SQL、调度 | ★★ | **首选入口**，SQL 为主，见效最快 |
| 大数据开发（离线/批处理） | 数据清洗、离线计算任务开发 | Spark（Scala/Java）、Hive | ★★★ | 第二目标，发挥 Java 优势 |
| 实时开发 | 实时指标、实时链路、风控 | Flink、Kafka、ClickHouse/Doris | ★★★★ | 进阶方向，薪资溢价高 |
| 数据平台 / 中间件 | 集群运维、组件二次开发、平台建设 | Hadoop 生态源码、K8s | ★★★★★ | 不建议作为首个目标 |

**推荐路径**：数仓开发 → Spark 开发 → 实时开发（Flink）。三个方向的知识是递进的，学完数仓再学 Spark/Flink 理解成本最低。

### 1.2 你的可迁移优势

- Java / Kotlin 功底 → Spark、Flink 都是 JVM 生态，很多团队直接写 Java/Scala
- JVM 内存模型、GC、多线程 → 直接用于 Spark/Flink 调优（这是很多转行者最缺的）
- 工程能力：构建、CI、日志、线上问题排查、组件化思维
- 业务理解：App 埋点、用户行为数据是你最熟悉的领域，可做差异化项目

### 1.3 必须补的短板

| 短板 | 说明 | 补齐方式 |
|---|---|---|
| Linux / Shell | 大数据任务 100% 跑在 Linux | 阶段一集中补 |
| SQL | 数仓开发的主战场，不是"会写 select" | 阶段一 + 贯穿全程刷题 |
| 分布式系统概念 | 分区、副本、容错、一致性、Shuffle | 阶段二起边学边建概念 |
| 数据建模 | 维度建模、分层、指标体系，Android 无对应概念 | 阶段三重点攻克 |
| 数据规模思维 | 从"单机 MB 级"到"集群 TB 级"的思维切换 | 通过项目刻意练习 |

### 阶段一：Linux + SQL 打底（W1–W2）

**目标**：能在 Linux 上自如操作文件与进程；SQL 能独立解决中等复杂度的分析需求。

| 周 | 学习内容 | 动手任务 | 验收标准 |
|---|---|---|---|
| W1 | Linux 常用命令（`grep/awk/sed/sort/uniq/join/cut`）、文件权限、进程管理（`ps/top/jps`）、`crontab`、SSH 免密、vim 基础 | 用 Shell 写一个 Nginx/App 日志清洗脚本：按天切分、按 URL 去重、统计 Top10 访问 | 脚本可在服务器上通过 crontab 每日自动执行 |
| W2 | SQL 强化：多表 join、子查询、CTE、**窗口函数**（`row_number/rank/lag/lead/sum over`）、行列转换、去重取最新、`explain` | 牛客 SQL 专项 + LeetCode 数据库 30~50 题 | 能独立写出"分组取 TopN""连续登录""同环比"三类经典题 |

**重点提醒**：窗口函数是数仓面试的第一考点，必须练到条件反射。

---

### 阶段二：Hadoop 生态 + Hive（W3–W5）

**目标**：理解 HDFS/YARN 的基本原理，能熟练使用 Hive 完成数据开发。

| 周 | 学习内容 | 动手任务 | 验收标准 |
|---|---|---|---|
| W3 | HDFS（读写流程、副本、块、小文件问题）、YARN（资源调度、Container、队列）、MapReduce 三阶段（只求理解，不写 MR） | Docker 起 Hadoop 伪集群，或用云服务器搭 3 节点 | 能通过 Web UI 观察 NameNode / ResourceManager，能上传下载文件 |
| W4 | Hive：库表、内部表 vs 外部表、分区、分桶、数据类型、Hive SQL 与 MySQL 差异 | 建分区表导入日志数据，完成 10 条统计 SQL | 能解释分区与分桶的区别及适用场景 |
| W5 | Hive 调优：数据倾斜、小文件合并、`map join`、动态分区、`distribute by / sort by`；Sqoop / DataX 数据同步 | 用 DataX 或 Sqoop 把 MySQL 数据同步到 Hive | 能说明一次数据倾斜的产生原因和 3 种解决思路 |

**环境建议**：本地 Docker（省钱）或 2C4G 云服务器（更真实）。不要在 Windows 原生环境折腾。

---

### 阶段三：数据仓库建模 + 调度（W6–W8）

**目标**：建立数仓思维，能独立设计一套分层模型并调度起来。**这是转岗最核心的壁垒。**

| 周 | 学习内容 | 动手任务 | 验收标准 |
|---|---|---|---|
| W6 | 数仓分层：ODS / DWD / DWS / ADS；为什么要分层；数据集市 | 画出你项目的分层架构图，说明每层职责 | 能回答"不分层行不行、分层带来什么代价" |
| W7 | 维度建模：事实表 vs 维度表、星型/雪花、四种事实表、SCD1/SCD2、**拉链表**、一致性维度、总线矩阵 | 为 App 埋点场景设计 DWD 明细模型 + 2 张维度表 | 能画出总线矩阵，能写出拉链表的实现 SQL |
| W8 | 指标体系（原子/派生/复合指标）、口径管理、数据质量校验、元数据与血缘；调度：**DolphinScheduler** | 用 DolphinScheduler 编排"ODS→DWD→DWS→ADS"四级任务链 | 调度 DAG 能自动跑通，支持补数和依赖 |

**教材**：《数据仓库工具箱（第 3 版）》前 8 章 + 《大数据之路：阿里巴巴大数据实践》。

---

### 阶段四：Spark（W9–W12）

**目标**：能用 Scala 编写 Spark 任务，理解 Shuffle 与调优手段。

| 周 | 学习内容 | 动手任务 | 验收标准 |
|---|---|---|---|
| W9 | Scala 基础：case class、模式匹配、高阶函数、集合操作、隐式转换（够用即可，不追求语言精通） | 用 Scala 完成 10 个小练习 | 能读懂 Spark 官方示例代码 |
| W10 | Spark 核心：RDD/DataFrame/Dataset、Transformation vs Action、惰性求值、DAG、宽窄依赖、Stage/Task | 用 RDD 和 DataFrame 各写一遍 WordCount 与日志清洗 | 能解释一个 Job 如何被切成 Stage |
| W11 | Shuffle 原理（Hash/Sort Shuffle）、持久化、广播变量、累加器、Spark SQL、与 Hive 集成 | 用 Spark SQL 完成 DWD 层清洗任务 | 能说明为什么 Shuffle 是性能瓶颈 |
| W12 | 调优：数据倾斜（加盐、两阶段聚合、`repartition`）、并行度、序列化（Kryo）、内存模型、`spark-submit` 参数 | 对一个倾斜任务做优化并记录前后耗时 | 能针对数据倾斜给出 3 种以上方案及取舍 |

**关键产出（写进简历）**：App 用户行为日志 → 清洗 → **会话切分（Session）** → UV/PV/留存/漏斗指标计算。

---

### 阶段五：Kafka（W13–W14）

**目标**：理解消息队列在数据链路中的角色，能保证数据不丢不重。

| 周 | 学习内容 | 动手任务 | 验收标准 |
|---|---|---|---|
| W13 | Kafka 架构：Broker、Topic、Partition、Replica、ISR、Consumer Group、Offset、Rebalance | 搭 Kafka，写生产者和消费者，模拟多分区多消费者 | 能画出一条消息从生产到消费的完整路径 |
| W14 | 可靠性：acks、幂等生产者、事务、消息丢失与重复的成因及对策 | 做"消费端手动提交 offset + 幂等写入"实验 | 能回答"如何保证 Exactly-once"（分生产端/消费端答） |

---

### 阶段六：Flink 实时（W15–W17）

**目标**：能独立开发一条实时统计链路。

| 周 | 学习内容 | 动手任务 | 验收标准 |
|---|---|---|---|
| W15 | Flink 基础：架构（JobManager/TaskManager/Slot）、DataStream API、算子、`keyBy/window/join`、并行度 | 写第一个 Flink 作业：Kafka 读取 → 简单聚合 → 打印 | 作业能在本地和集群模式跑通 |
| W16 | **Watermark 与乱序处理**、窗口类型、状态管理（Keyed State、State Backend）、侧输出流 | 处理乱序数据并用侧输出流收集迟到数据 | 能解释 Watermark 的作用与迟到数据的三种处理方式 |
| W17 | **Checkpoint / Savepoint / Exactly-once**、反压（Backpressure）、维表 Join、Flink SQL / Table API | 用 Flink SQL 实现实时 UV 统计并写入 MySQL/Doris | 能解释 Checkpoint 原理及与 Spark 批处理的差异 |

## 三、端到端实战项目（简历核心）

### 3.1 项目选题：App 埋点用户行为分析平台

利用你的 Android 背景，这是最能讲出业务深度、又天然覆盖全链路的项目。

```
App 埋点 SDK（你熟悉）
   → 日志采集（Filebeat / Flume）
   → Kafka（缓冲 + 解耦）
   → Flink 实时清洗 & 会话切分
        ├── 实时指标 → ClickHouse / Doris → 可视化大屏
        └── 明细落 HDFS / Hive
   → Spark 离线任务（留存、漏斗、用户画像）
   → 数仓分层 ODS / DWD / DWS / ADS
   → DolphinScheduler 调度
   → BI 展示（Superset / 自研）
```

### 3.2 里程碑拆分

| 里程碑 | 内容 | 对应阶段 |
|---|---|---|
| M1 | 采集 + Kafka 链路打通，数据可查 | W13–W14 |
| M2 | Spark 离线清洗，DWD 明细层成型 | W12 |
| M3 | 数仓分层 + 调度自动化，指标可产出 | W8 |
| M4 | Flink 实时链路 + OLAP 查询 + 看板 | W17–W18 |
| M5 | 监控告警、补数方案、性能优化记录 | W18 |

### 3.3 简历写法示例

> 基于 Flink + Kafka + Hive + Doris 搭建 App 用户行为分析平台，完成埋点采集到指标可视化的全链路，支撑 DAU、留存、漏斗等 20+ 指标，日均处理日志约 5000 万条。
> 针对数据倾斜与乱序问题，通过加盐 + 两阶段聚合、Watermark + 侧输出流解决，任务稳定性显著提升；通过引入 Doris 物化视图，看板查询 P95 从 8s 降至 800ms。

**写作要点**：技术选型理由 + 你解决的问题 + **可量化结果**，三者缺一不可。

## 五、常用术语手册

### 5.1 岗位与通用

| 术语 | 全称 / 英文 | 含义 |
|---|---|---|
| 大数据开发 | Big Data Engineer | 负责数据采集、清洗、计算任务的开发与运维 |
| 数仓开发 | Data Warehouse Engineer | 负责数仓分层建模、ETL、指标开发 |
| ETL | Extract-Transform-Load | 抽取-转换-加载，传统离线数据处理流程 |
| ELT | Extract-Load-Transform | 先入湖/仓再计算，现代大数据主流模式 |
| 数据治理 | Data Governance | 数据质量、元数据、血缘、安全、标准的统称 |
| 数据质量 | Data Quality | 完整性、准确性、及时性、一致性、唯一性 |
| 元数据 | Metadata | 描述数据的数据（表结构、分区、血缘、负责人） |
| 数据血缘 | Data Lineage | 数据从源表到目标表的流转关系，用于影响分析 |
| 数据倾斜 | Data Skew | 某 key 数据量远大于其他，导致单 task 拖慢整个作业 |
| 幂等 | Idempotence | 同一操作执行多次结果一致，重跑/重试的基础 |
| 补数 | Backfill | 对历史分区重新跑任务，修正缺失或错误数据 |
| 口径 | Metric Definition | 指标的计算定义，必须全公司统一，否则数据对不上 |
| SLA | Service Level Agreement | 数据产出时间与可用性承诺，如"每日 7 点前产出" |

### 5.2 Hadoop 生态

| 术语 | 全称 / 英文 | 含义 |
|---|---|---|
| Hadoop | — | 分布式存储 + 计算基础框架，包含 HDFS/YARN/MapReduce |
| HDFS | Hadoop Distributed File System | 分布式文件系统，主从架构（NameNode + DataNode） |
| NameNode | — | HDFS 元数据节点，记录文件与块的映射 |
| DataNode | — | HDFS 数据节点，实际存储数据块 |
| Block | 数据块 | HDFS 最小存储单元，默认 128MB |
| 副本 | Replication | 每个块默认存 3 份，保证容错 |
| 小文件问题 | Small File Problem | 大量小文件导致 NameNode 元数据压力大、计算效率低 |
| YARN | Yet Another Resource Negotiator | 集群资源调度框架 |
| ResourceManager | — | YARN 主节点，负责全局资源分配 |
| NodeManager | — | YARN 从节点，管理单机资源 |
| Container | 容器 | YARN 的资源分配单位（CPU + 内存） |
| MapReduce | — | 批处理计算模型，分 Map / Shuffle / Reduce 三阶段 |
| Hive | — | 建立在 Hadoop 上的 SQL 数仓工具，SQL 转 MapReduce/Spark/Tez |
| Hive Metastore | — | Hive 元数据服务，存储库表结构，被众多引擎共享 |
| 内部表 / 外部表 | Managed / External Table | 内部表删表删数据；外部表只删元数据，数据保留 |
| 分区 | Partition | 按目录切分数据（如按天），查询剪枝的关键 |
| 分桶 | Bucket | 按 hash 把数据切到固定数量文件，利于 join 和抽样 |
| HBase | — | 基于 HDFS 的分布式列式 NoSQL 数据库，支持随机读写 |
| ZooKeeper | — | 分布式协调服务，用于选主、配置、锁 |
| Sqoop | — | 关系型数据库与 Hadoop 之间的批量数据同步工具 |
| DataX | — | 阿里开源异构数据同步工具，国内常用 |
| Flume | — | 日志采集与聚合工具 |
| Oozie / Azkaban | — | 早期工作流调度工具，现多被 DolphinScheduler 替代 |

### 5.3 数据仓库建模

| 术语 | 全称 / 英文 | 含义 |
|---|---|---|
| 数据仓库 | Data Warehouse | 面向分析、集成、随时间变化、不可更新的数据集合 |
| 数据集市 | Data Mart | 面向某业务线的子集数仓 |
| ODS | Operational Data Store | 贴源层，原始数据几乎不做加工 |
| DWD | Data Warehouse Detail | 明细层，清洗、规范化后的明细数据 |
| DWS | Data Warehouse Summary | 汇总层，按主题/维度做轻度聚合 |
| ADS | Application Data Service | 应用层，直接服务报表与接口的指标结果 |
| DIM | Dimension | 公共维度层，统一维度定义 |
| 维度建模 | Dimensional Modeling | Kimball 提出的面向分析的建模方法 |
| 事实表 | Fact Table | 记录业务过程的度量值（如订单金额、点击次数） |
| 维度表 | Dimension Table | 描述事实的上下文（如用户、商品、时间） |
| 星型模型 | Star Schema | 事实表 + 扁平维度表，查询性能好，推荐 |
| 雪花模型 | Snowflake Schema | 维度表再规范化拆表，减少冗余但 join 多 |
| 总线矩阵 | Bus Matrix | 业务过程 × 维度的一致性规划矩阵 |
| 一致性维度 | Conformed Dimension | 全公司统一定义、可复用的维度 |
| 粒度 | Granularity | 一行数据代表的业务细节程度，建模第一步要定粒度 |
| SCD | Slowly Changing Dimension | 缓慢变化维，维度属性随时间变化 |
| SCD1 | — | 直接覆盖，不保留历史 |
| SCD2 | — | 新增一行记录版本，保留历史 |
| 拉链表 | Zipper Table | 用 `start_date/end_date` 保存全量历史状态，SCD2 的经典实现 |
| 退化维度 | Degenerate Dimension | 存放在事实表中的维度键（如订单号） |
| 原子指标 | Atomic Metric | 不可再拆的基础度量，如"支付金额" |
| 派生指标 | Derived Metric | 原子指标 + 修饰词 + 时间周期，如"近 7 日 Android 支付金额" |

## 七、避坑清单

1. **不做"全家桶学习者"**：Hadoop 生态名词成百上千，抓住 Hive + Spark + Flink + 一个 OLAP 即可。
2. **不要长期停在伪集群**：真实多节点踩过的坑，比看十篇文章有用。
3. **不要丢掉 Java 优势**：别为了"看起来像大数据"去转 Python，JVM 是你的差异化。
4. **不要只学不做**：每个阶段必须有可运行的产出，否则面试讲不出细节。
5. **不要等学完再投简历**：完成 Spark 阶段（W12）就可以开始试投，用面试反馈校准学习重点。
6. **优先内部转岗**：公司若有数据团队，主动接一个数据需求是最快的转型路径。
7. **不要迷信八股**：初级岗位拼的是"能干活 + 讲清楚项目"，八股只是门槛。
